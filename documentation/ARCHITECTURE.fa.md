# معماری نسخه آنلاین

مرجع کد: [`hosted/`](../hosted/). نمونه Python و GitHub Pages مسیرهای مستقل‌اند؛ هیچ همگام‌سازی داده خودکاری بین آن‌ها وجود ندارد.

## اجزا

| مسیر در hosted | مسئولیت |
|---|---|
| `app/page.tsx`, `app/chatgpt-auth.ts` | صفحه ورودی و استخراج هویت معتبر درگاه |
| `app/workspace.tsx` | ناوبری، فضای تست/واقعی، دریافت داده و ثبت فرم‌ها |
| `app/visual-library.tsx` | انتخاب ماده و الگوی دستور، فرم مرحله‌ای |
| `app/inventory.tsx` | خرید، موجودی هر نوبت و دورریز |
| `app/trading.tsx` | ترکیب مواد، فروش و گزارش روز |
| `app/api/data/route.ts` | API، کنترل هویت و محدوده مجموعه، اعتبارسنجی و نوشتن |
| `lib/library.ts` | کتابخانه مواد و دستورهای پیشنهادی |
| `lib/cost.ts`, `lib/stock.ts` | پول، مقدار، بازده، تاریخ و مقیاس موجودی |
| `lib/operations.ts` | ترکیب، تخصیص خریدها و ثبت فروش اتمی |
| `lib/demo.ts` | داده فرضی و ورود بدون تکثیر نمونه‌ها |
| `db/schema.ts`, `drizzle/` | تعریف جدول و تاریخچه مهاجرت |
| `tests/operations.test.mjs` | آزمون محاسبات و نمونه‌ها با SQLite حافظه‌ای |

پشته فعلی React 19، TypeScript، Vinext/Vite، اجزای Shadcn و Cloudflare D1 است. نسخه دقیق در package.json و pnpm-lock.yaml قرار دارد. API به binding منطقی `DB` دسترسی دارد. R2 استفاده نمی‌شود.

## جریان درخواست

مرورگر از `/api/data` داده می‌گیرد و JSON ثبت می‌کند. هویت از headerهای درگاه معتبر گرفته می‌شود؛ انتخاب مجموعه از هویت سرور است، نه restaurant_id ارسالی کاربر. `?demo=1` همان حساب را در محدوده تستی جدا قرار می‌دهد. این جداسازی منطقی در یک پایگاه است، نه پایگاه جداگانه.

GET تغییری نمی‌دهد. هنگام ورود به فضای تستی، رابط ابتدا POST با `kind=seed_demo` می‌فرستد. داده‌ها در D1 می‌مانند. قابلیت WebMCP موجود فقط خواندن رکوردهای فضای فعلی است؛ چت‌بات یا ابزار ویرایش نیست.

## فروش و تراکنش

۱. دستور با شرط شناسه مجموعه خوانده می‌شود؛ مقدار اختیاری مصرف روی کپی دستور اعمال می‌شود.
۲. ترکیب‌ها به اجزای ساده شکسته و نیاز هر هویت ماده جمع می‌شود.
۳. خریدها با همان هویت و واحد، به ترتیب تاریخ تخصیص می‌یابند. تاریخ گذشته حذف می‌شود.
۴. درج sale فقط وقتی مجاز است که تمام خریدهای تخصیص‌یافته هنوز موجودی کافی داشته باشند.
۵. کاهش هر lot فقط در حضور sale اعمال‌نشده انجام می‌شود؛ سپس `data.applied=true` می‌شود.
۶. همه نوشتن‌ها در یک D1 batch هستند. نبود موجودی مانع درج و کاهش است؛ خطای batch باید همه تغییرات آن batch را برگرداند.

شناسه درخواست در فرم تا پایان عملیات نگه داشته می‌شود. تکرار همان sale ثبت‌شده دوباره مصرف نمی‌کند. هنگام خطای HTTP زیر ۵۰۰ رابط شناسه را پاک می‌کند؛ خطاهای شبکه آن را حفظ می‌کنند. این قرارداد برای تلاش مجدد همان عملیات است، نه تغییر payload با شناسه قبلی.

دورریز مسیر جدا با stock_moves دارد: درج مشروط، کاهش موجودی وقتی applied=0 و سپس applied=1 در batch. فروش‌ها stock_moves ایجاد نمی‌کنند؛ رد مصرف آن‌ها داخل sale.allocations است.

## تصمیم‌های طراحی و پیامدها

- **نسخه قیمت:** خرید و ثبت ماده، قیمت تازه می‌سازند؛ رسپی قبلی تغییر نمی‌کند. هزینه فروش از lot واقعی مصرف‌شده است و ممکن است با برآورد رسپی فرق کند.
- **ترکیب داخلی:** به‌جای انبار ترکیب آماده، اجزای خام مصرف می‌شوند. تولید بچ و مخلوط تودرتو نیاز به طراحی بعدی دارند.
- **records به‌صورت JSON:** توسعه اولیه ساده‌تر است؛ اعتبارسنجی و رابطه بسیاری از فیلدها فقط در برنامه انجام می‌شود.
- **اولویت انقضا:** تاریخ نامشخص آخر صف است، اما ممنوع نیست. موتور تأیید سلامت غذا نیست.
- **فرم فارسی ساده:** مبلغ ورودی تومان، ذخیره ریال؛ واحد مصرف فقط گرم، میلی‌لیتر و عدد.
- **انتشار دوگانه:** GitHub آرشیو کد عمومی است؛ انتشار سایت از مخزن منبع Sites و نسخه بسته‌بندی‌شده انجام می‌شود. صرف push به GitHub برنامه آنلاین را به‌روز نمی‌کند.

## مرزهای فعلی

صفحه‌بندی API، پردازش پس‌زمینه، import، کش قیمت، تسویه پلتفرم، عضویت کارکنان، بازیابی رویداد و audit جامع پیاده نشده‌اند. گزارش‌ها در مرورگر از داده برگشتی ساخته می‌شوند. برای بزرگ‌شدن داده، تجمیع سمت سرور و صفحه‌بندی باید پیش از اتکای عملیاتی اضافه شوند.
