# توسعه، اجرا و عملیات

## مسیرها

نسخه اصلی آنلاین در `hosted/` است. `app.py` و `diner_core/` نمونه قدیمی Python هستند. `docs/` صفحات عمومی GitHub Pages را دارد. مستندات در `documentation/` هستند تا فایل index.html پیش‌نمایش جابه‌جا نشود.

## نصب و بررسی آنلاین

نیاز: Node >=22.13، pnpm طبق packageManager فعلی (11.25.0). نسخه‌های دقیق وابستگی را از lockfile بگیرید؛ ابزار مدیریت بسته را بدون نیاز تغییر ندهید.

```bash
git clone https://github.com/nimania/diner.git
cd diner/hosted
pnpm install --frozen-lockfile
pnpm exec tsc --noEmit
node tests/operations.test.mjs
pnpm build
```

تست از node:sqlite و فایل‌های migration استفاده می‌کند. در برخی نسخه‌های Node این ماژول هشدار آزمایشی می‌دهد. خروجی موقت تست شامل `/tmp/diner-sale-statements.json` است. این تست به کلید Cloudflare یا پایگاه واقعی متصل نمی‌شود.

`pnpm dev` برای توسعه و `pnpm start` برای اجرای build محلی با Wrangler تعریف شده‌اند. اجرای UI دارای ورود در محیط مستقل، نیازمند سازوکار هویت امن است؛ قرار دادن header ساختگی در یک سرور عمومی راه‌حل نیست. داده پایدار محلی Wrangler از داده آنلاین D1 جداست. اجرای migration محلی را با پیکربندی همان محیط انجام دهید؛ کد به‌صورت خودکار schema تولید نمی‌کند.

در محیط مدیریت‌شده Sites، ابزارهای افزونه پروفایل اجرا و build را تنظیم می‌کنند؛ مسیر نصب آن ابزارها جزو پیش‌نیاز عمومی clone نیست. به اسکریپت‌ها و پیکربندی موجود پروژه احترام بگذارید.

## نمونه قدیمی Python

از ریشه مخزن با Python 3.10+:

```bash
python app.py
python -m unittest discover -s tests -v
```

برنامه قدیمی روی loopback و پورت 8765 اجرا می‌شود. SQLite آن در `private-data/diner.sqlite3` است و نباید commit شود. این پایگاه، D1 برنامه آنلاین نیست. جزئیات بیشتر در DEVELOPMENT.md قدیمی است؛ آن سند رفتار hosted را تعریف نمی‌کند.

## مهاجرت

در hosted بعد از تغییر db/schema.ts:

```bash
pnpm db:generate
```

SQL و journal/snapshot ایجادشده را مرور کنید. مهاجرت اعمال‌شده تغییر نمی‌کند. هر prepare باید یک statement داشته باشد؛ عملیات چندمرحله‌ای از batch استفاده کنند. seed را در migration نریزید. نسخه آنلاین فعلی برای منوی عمومی جدول جدیدی لازم ندارد و از records استفاده می‌کند.

## انتشار

- GitHub Pages محتوای `docs/` را سرو می‌کند؛ بررسی تنظیمات Pages و وضعیت workflow انتشار لازم است.
- برنامه آنلاین روی Sites منتشر می‌شود، نه GitHub Pages. مالک سایت نسخه منبع را در مخزن منبع Sites ثبت می‌کند، build متناظر را بسته‌بندی می‌کند و همان commit را save/deploy می‌کند.
- GitHub و مخزن منبع Sites دو مقصد‌اند؛ تغییر کد GitHub به‌تنهایی انتشار آنلاین نیست. تغییر صرفاً مستندات نیاز به انتشار دوباره برنامه ندارد.
- به project موجود و audience فعلی احترام بگذارید. عمومی‌کردن کد به معنی عمومی‌کردن سایت یا DB نیست.
- credential فقط در header همان فرمان انتقال استفاده شود؛ در remote URL، فایل، log یا README نرود.
- موفقیت فقط با وضعیت نهایی succeeded و URL اعلام‌شده تأیید می‌شود؛ pending یا build موفق کافی نیست.

## پایگاه داده فعلی کجاست؟

**نسخه آنلاین: Cloudflare D1 در زیرساخت Sites، با binding منطقی DB.** فایل داده داخل گیت‌هاب نیست. حساب واقعی و تستی در همان DB با restaurant_id و owner جدا هستند. `r2` غیرفعال است. منطقه فیزیکی، شناسه حساب Cloudflare، برنامه backup و SLA از فایل‌های این پروژه مشخص نمی‌شوند؛ در این مستندات برای آن‌ها تضمینی اعلام نمی‌شود.

**نمونه Python:** فایل SQLite محلی. **GitHub Pages:** صفحه ایستا بدون دسترسی به D1؛ منوی عمومی از داده عمومی تعبیه‌شده در لینک خوانده می‌شود.

## بازیابی و عیب‌یابی

- خطای دریافت: ورود و دسترسی حساب، binding DB و وضعیت مهاجرت را بررسی کنید. اطلاعات شخصی log را عمومی نکنید.
- کسری موجودی: واحد، بازده، هویت ماده، مقدار واقعی و انقضا را بررسی کنید. خرید فرضی در مجموعه واقعی ایجاد نکنید.
- مشاهده‌نشدن فروش تستی: روز ایجاد نمونه را در گزارش انتخاب کنید؛ seed روزها را بازنویسی نمی‌کند.
- خرابی انتشار: علت نهایی را بخوانید. اگر migration ممکن است اعمال شده باشد، قبل از تغییر SQL وضعیت واقعی را بررسی کنید.
- rollback کد مساوی rollback داده نیست. restore داده باید با امکان رسمی میزبانی و پس از بررسی داده‌های بعد از نقطه بازیابی انجام شود.

backup خودکار، export کامل و تست restore در محصول فعلی پیاده/تأیید نشده‌اند. قبل از بهره‌برداری جدی، راهکار backup و تمرین restore جزء معیار پذیرش است.
